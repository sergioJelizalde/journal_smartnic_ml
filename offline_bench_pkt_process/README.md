# tracking_bench — DPDK stateful-tracking benchmarks (inference removed)

Three self-contained DPDK applications that isolate the *stateful tracking*
cost of the three workloads in the JNCA paper. The MLP inference path has
been completely removed; feature vectors are still constructed when a window
completes (that cost belongs to the data path) and are folded into a
volatile sink so the compiler cannot elide them. A later merge step will
re-attach the scalar/NEON/XNNPACK kernels for the end-to-end numbers.

The three cases and what each one stresses:

**Case A — `bench_tcp_flow`** (from `iot_mlp/iot_multicore.c`). TCP-only
per-flow tracking. Every IPv4/TCP packet performs one hash lookup on a
canonicalized 5-tuple and updates length/IAT/flag statistics; every
`TCPF_N_PACKETS` (default 6) packets an 8-feature vector is built. This is
the *highest table-pressure* case: every packet is a tracked event, and the
cost is dominated by `rte_hash` lookup plus one cache line of per-flow state.

**Case B — `bench_tls_appdata`** (from `doh_mlp/doh_multicore.c`). TLS
Application-Data parsing plus bidirectional tracking. Packets are filtered
to port 443 and TLS record type 23; the record length comes from the TLS
header, and per-flow state is split by direction (client/server counts,
bytes, length min/max/sum, direction switches) over 64-record windows. This
case adds *payload parsing* and roughly doubles the per-flow state footprint
relative to Case A, with the 16-feature build at window close.

**Case C — `bench_modbus`** (from `ics_modbus/modbus.c`). Modbus/TCP
transaction tracking. Requests (function codes 0x03/0x04) are recorded in a
pending-request tracker; responses are matched by (transaction_id, unit_id),
each register decoded, and readings inserted into per-(unit_id, reg_addr)
circular windows of 32 samples carrying persistent CUSUM/EWMA state. This is
the *deepest state machine*: two coupled tables (transactions + sensors),
multi-record fan-out per packet, and the most expensive feature computation
(regression slope, EWMA recurrence, CUSUM over the window).

## Generalization changes vs. the originals

The three originals had drifted apart in boilerplate while sharing 60%+ of
their code. Everything protocol-agnostic now lives in `bench_common.h`: EAL
and port init, symmetric RSS configuration, the RX/TX run loop, counters,
sampled cycle instrumentation, percentile reporting, signal handling, and
CLI parsing. Each workload is reduced to its key/entry structs, a
`proc_burst` parser, and an init hook, wired through a small `bench_ops`
vtable (the indirect call is per burst, not per packet, so it costs nothing
measurable).

Substantive fixes worth stating in the paper: (1) the Modbus pending-request
tracker is now per-core and lock-free instead of a single global spinlocked
array — the symmetric Toeplitz RSS key (0x6D5A repeated) guarantees that
both directions of a TCP connection land on the same queue, so request and
response always meet on the same core, and the original's per-PDU global
spinlock (which would have serialized all cores and poisoned any multicore
scaling result) is gone. (2) Case A windows now roll over by default instead
of finalizing a flow forever, so steady-state throughput includes the
recurring feature-build cost, matching Cases B and C; compile with
`-DTCPF_WINDOW_MODE=0` to restore finalize-once. (3) All per-packet
`printf`/CSV logging is out of the hot path; instrumentation is
reservoir-sampled (one `rdtsc` pair per Kth tracked event, default K=64)
plus an always-on per-burst cycle count, so the measurement overhead is
bounded and identical across the three cases. (4) Counters that were
previously plain globals shared across cores (a data race in the originals)
are per-worker.

## Build

```bash
make                       # x86 host
# BlueField-3: uncomment the -mcpu=cortex-a78ae line in the Makefile
make EXTRA_CFLAGS='-DTCPF_N_PACKETS=6 -DTLSB_N_RECORDS=64 -DMB_WINDOW_SIZE=32'
```

## Run

```bash
# 8 worker cores, one RX queue each, 60 s run, forward mode:
./build/bench_tcp_flow    -l 0-7 -a <PCI_BDF> -- -d 60 -o results/run1
./build/bench_tls_appdata -l 0-7 -a <PCI_BDF> -- -d 60 -o results/run1
./build/bench_modbus      -l 0-7 -a <PCI_BDF> -- -d 60 -o results/run1
```

Options after `--`: `-d <s>` duration (0 = until Ctrl-C), `-s <k>` sample
one of every k tracked events (0 disables), `-f 0|1` drop vs. MAC-swap
forward, `-o <prefix>` output file prefix. Each run writes
`<prefix>_<case>_summary.csv` (per-core throughput, hit/update/insert
counters, event-latency percentiles, cycles/packet) and
`<prefix>_<case>_samples.csv` (raw sampled event cycles for CDFs).

## Proposed JNCA experiment design

**Testbed.** BlueField-3 DPU (16× Cortex-A78AE ARM cores) as the device
under test, DPDK 23.x, traffic generated by TRex on a directly attached
server over 100 GbE (the FABRIC topology already used for the DoH work).
Report exact firmware, DPDK version, hugepage config, and core isolation.

**Traffic profiles.** One profile per case, generated with TRex ASTF so
that the stateful semantics are exercised realistically: (A) mixed TCP flows
with a configurable number of concurrent flows and packets per flow; (B)
TLS-like flows on port 443 whose payloads carry syntactically valid
Application-Data record headers, with a controllable client/server record
mix; (C) Modbus request/response pairs (fc 0x03/0x04) across a configurable
number of (unit_id, register) sensor streams, several registers per
response. Fix the packet-size distribution across cases when comparing them
so parse cost differences are attributable to the protocol, not the frame
size, and additionally report a 64 B worst case for Case A.

**Factors (full factorial where feasible).**

| Factor | Levels | Purpose |
|---|---|---|
| Workload | A, B, C | main comparison |
| Worker cores | 1, 2, 4, 8, 16 | scaling; RSS efficacy |
| Offered load | 10%→line rate in steps | find saturation knee |
| Concurrent keys | 1k, 10k, 100k, 500k flows / sensors | cache-vs-DRAM table pressure |
| Window length | A: 4/6/8 pkts; B: 16/64/128 rec; C: 16/32/64 samples | amortization of feature build |
| Forward mode | fwd, drop | isolate TX cost |

**Metrics.** Per run: sustained throughput (Mpps and Gbps) at zero loss
(binary-search the offered load, RFC 2544 style, 3 trials, report
mean ± std); per-event tracking latency p50/p90/p99/p99.9 in ns from the
sampled reservoir (CDF figure, one curve per case); mean cycles/packet from
the burst counters (decomposable: cycles/packet vs. cycles/tracked-event
separates parse-filter cost from table cost); table occupancy and insert
failures (validity check); windows/s (feature-build rate). For Case C also
report request→response match rate and pending-tracker occupancy.

**Procedure.** For each configuration: 10 s warm-up (table fill), 60 s
measurement window, 3 repetitions, fresh process per repetition so tables
start cold consistently. Pin workers with `-l`, keep the main lcore on an
isolated core, disable frequency scaling, record `rte_get_tsc_hz()`.

**Proposed figures/tables for the paper.** (1) Grouped bar chart: max
zero-loss throughput per case at 1/4/8/16 cores — the headline scaling
result, expected near-linear for A/B given per-core tables, and now also
for C after the lock removal (a before/after with the global-lock variant
makes a strong ablation). (2) CDF of per-event tracking latency, three
curves, log-x — visualizes the cost ordering A < B < C and the C tail from
multi-register fan-out. (3) Line plot of cycles/packet vs. concurrent keys —
shows the L2/LLC/DRAM transitions of `rte_hash`. (4) Table: per-case
breakdown of cycles/packet into parse+filter (all packets) vs. track
(hit packets) vs. feature build (windows), derived from the counters. (5)
Sensitivity line plot: throughput vs. window length, demonstrating
feature-build amortization. Once the inference kernels are merged back,
the same harness re-runs with scalar/NEON/XNNPACK to yield the end-to-end
"tracking + inference" figure, and the delta against these numbers cleanly
attributes cost to inference.
